# 04. 应用启动配置管理

> **IDFA / Adjust**：配置中的 `adjustToken` 拉取完成后，须配合 `HQTIDFAAdjustCoordinator.initializeAdjustIfNeeded()` 完成 SDK 注册；全流程见 `24-IDFA与Adjust初始化流程.md`。（启动时序与缓存策略）

## 4.1 核心目标
- 避免首次启动黑屏与首屏阻塞。
- 确保配置与文案在需要前可用，并支持失败降级。
- **域名优先**：本地若无已校验通过的可用 API 基址，须在启动链路中**立即**触发域名拉取（不依赖用户进入某页面后再请求）。细则见下文与 `02-基础网络请求规范.md` §2.6。

## 4.2 启动时序（必须按序理解；实现上可与首屏并行）

### 4.2.1 域名（最先调度，逻辑上先于一切业务接口）
- **触发时机**：应用完成冷启动并进入前台展示首屏后（如 `Scene` 已连接、`window` 已 `makeKeyAndVisible`），由统一的启动管理器（如 `HQEAppStartupManager`）**立刻**调度一次 `ensureDomainReady`（名称以工程为准）。
- **行为**：
  1. 若内存或持久化中已有**当前可用**域名，则校验通过后直接使用，不再重复拉源。
  2. 若**无缓存**、或缓存**校验失败**、或**从未成功写入**可用域名：必须**马上**按「域名源列表」顺序请求远端 README/配置源，解析、规范化（含 `eeee`/`ffff`/`aaaa` 规则，见 `00-项目基础规范.md` §00.9.2 与 `02-基础网络请求规范.md` §2.6.7）、健康检查通过后写入缓存并作为当前 API 基址。
  3. **禁止**：等到用户点击「获取验证码」等业务操作时才首次去拉域名（除非启动调度已失败且业务层做补偿重试）。
- **失败降级**：域名全流程失败时，后续 `/app/v3/app/config` 等请求会失败；启动管理器可记录日志/埋点，但**不**阻塞首屏 UI 渲染（与 §4.3 一致）。

### 4.2.2 应用配置与文案（依赖域名就绪后由网络层拼接完整 URL）
1. 获取基础配置接口：`/app/v3/app/config`
2. 获取文案分类接口：`/app/v3/category/gory`
3. 将配置与文案缓存到本地，供离线/失败降级使用
4. Scene 根页面直接进入首页；未登录为访客 UI（不拉首页业务接口），需登录时 Modal 登录页（见 `02-首页Loan.md` §2.3.5）

## 4.3 异步化要求（性能）
- Scene 生命周期里尽量先显示 UI，再**后台异步**执行：域名就绪 → 配置/文案拉取（由启动管理器串联，避免主线程阻塞）。
- 域名拉取与配置拉取均不得阻塞主线程绘制首帧；但调度上须「启动后尽快发起」，满足 §4.2.1「无可用域名则立即远端请求」。
- 首页加载阶段移除全屏 loading 以提升首屏可感知性。

## 4.4 本地缓存
- **域名**缓存键（示例）：`HQE_CACHED_DOMAIN`（与 `HQEDomainManager` 实现一致）；持久化，校验失败则清除并重新拉源。
- 应用配置缓存键：`UserDefaultKeyAppConfig`
- 文案配置缓存键：`UserDefaultKeyCategoryConfig`
- 更新策略：网络成功后更新缓存；失败使用旧缓存（域名失败时无旧缓存则保持空直至下次成功）。

## 4.5 启动阶段通知能力接入（与推送文档联动）
- 启动链路需并行接入通知基础能力，但不得阻塞首屏展示：
  1. `willFinishLaunching`：确保 Firebase Core 已 configure（防 `I-COR000003`）。
  2. `didFinishLaunching`：设置 `UNUserNotificationCenter` / `FIRMessaging` 代理；若已授权则注册 APNs。
  3. `sceneDidBecomeActive`：执行通知权限重校验与 token 补偿上报。
- 冷启动不直接弹系统通知权限；统一由首页弹窗链末位触发权限请求。
- 详细实现、token 链路与上报口径见 `06-通知与推送能力实现.md`。
